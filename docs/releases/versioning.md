主版本区分产品线。兼容修复增加修订号，新增功能增加次版本；需要改变产品线约定时先取得用户明确决定。旧四人版1.3.0+aee3b3f是规则生效前的历史版本，其Git标签保留，不再沿该版号发布四人包。四人GitHub发布入口迁到2.0.0+aee3b3f，安装包内部版本同步更新。

version.properties是当前分支唯一版本权威，保存三段版本、Android versionCode和获批功能Source的完整SHA。Gradle生成“版本号+短SHA”；构建元数据不参与SemVer优先级比较。GitHub预发布状态用于测试/预览版，不代表真实设备验收全部通过。

两条线沿用相同Android包名及分发证书，新打包的versionCode全局严格递增，不能各分支独立重用。已分发code7属于双人1.2.3+f587472；四人2.0.0+aee3b3f使用code8；之后新包至少code9。将同一个已安装测试APK原样上传GitHub，沿用既有版本、code与SHA256，不视为重新签发；禁止用旧身份覆盖不同字节或功能。

功能后缀固定为用户批准且选择发布的Source。打包提交可以晚于Source，但之后只允许版本、文档、发布证据和CI范围整理；功能修改必须重新审查并更新基线。标签指向实际打包源码，不移动已发布历史标签。

发布顺序：确认获批Source在目标长期分支历史中 → 核验打包差异与全局code → 完成相称的测试/Lint/构建、只读审查及CI → 正常合并目标分支 → 沿用分发证书签名，核验版本/非debuggable/签名/对齐/SHA256 → 创建不可变的v版本号+短SHA标签 → 上传APK及校验文件 → 核验远端资产。

已有同字节APK及固定Source验证可以复用，必须记录原打包提交和证据范围。双人1.2.3复用KUM-85包；四人2.0.0重新构建及签名。发布说明保留未完成的双机、蓝牙或道路验收，不把历史实测当本轮实测。

两条线通过独立PR变更，Android CI覆盖main及four-person。正常合并保留历史，不force push，不把四人协议/功能直接合回双人线。发布、合并及签名以用户明确授权为准；Rasen只管理合同、验证与证据，不自行授权发布。
