## 1. 背景与问题

MotoCom 面向骑行中的一对一实时对讲。发动机、道路、头盔内气流和麦克风直吹会同时影响语音输入，其中风噪具有非平稳、低频占比高、容易引起语音失真或削波等特点。

当前工程已经有 WebRTC 音频链路和基础 3A 能力：

- 使用 `stream-webrtc-android:1.3.9`。
- `RiderAudioEngine` 使用 `JavaAudioDeviceModule`，开启硬件 AEC、硬件 NS、低延迟和高通滤波请求。
- 当前 `SamplesReadyCallback` 只用于计算音量和 VOX 相关状态，不修改发送给远端的音频样本。
- Opus 已配置为单声道、32 kbps、FEC 和 DTX。
- `AudioSessionController` 统一拥有音频会话和路由生命周期。

现状代码参考：

- [RiderAudioEngine.kt](../../app/src/main/java/com/kuma/motointercom/RiderAudioEngine.kt#L348)
- [RiderAudioEngine.kt](../../app/src/main/java/com/kuma/motointercom/RiderAudioEngine.kt#L399)
- [AudioSessionController.kt](../../app/src/main/java/com/kuma/motointercom/AudioSessionController.kt)
- [app/build.gradle.kts](../../app/build.gradle.kts#L49)

当前主要问题不是“有没有基础降噪”，而是：

1. 尚未确认不同设备上硬件 NS 是否真正可用且效果一致。
2. 尚未建立专门针对头盔和行驶风噪的录音、指标和人工听音基线。
3. 尚未接入可修改 WebRTC 捕获音频的稳定原生处理点。
4. 不能通过现有 `SamplesReadyCallback` 直接实现发送前滤波。
5. 仅靠固定低频切除可能损伤男声和语音起始音，不能作为完整风噪方案。

## 2. 产品目标

### 2.1 用户目标

- 骑行通话时，远端能更清楚地听到本地语音。
- 在怠速、道路行驶和中等风噪下，降低持续背景噪声和风噪感。
- 语音清晰度提升不能以明显机器人音、吞字、爆音或通话延迟为代价。
- 目标蓝牙头盔麦克风路线具备安全降级能力；手机麦克风和 BLE Audio 只作为后续探索路线。
- 用户不需要理解 APM、RNNoise 或硬件 NS；产品默认自动选择经过验证的模式。
- 本 PRD 只处理本地麦克风上行音频，即远端车友听到的声音；不处理本地耳机下行播放音频。
- 如果 WebRTC APM 已满足本 PRD 验收条件，RNNoise 不属于首版必做项。

### 2.2 工程目标

- 保留现有 WebRTC、Opus、AEC、音频路由和会话生命周期。
- 将自定义降噪接入现有捕获链路，不创建第二套 `AudioRecord`。
- 先用 WebRTC APM 做稳定基线；只有 APM 未达到目标时才继续 RNNoise 或其他算法验证，避免为使用开源项目而增加无必要的维护成本。
- `BASELINE` 固定为当前代码原样：现有硬件 AEC/NS、WebRTC APM 配置、音频路由、Opus 和媒体会话行为均不变。
- 建立可重复的风噪测试集、设备矩阵和人工听音流程。
- 处理过载、初始化失败或设备不支持时，自动回退到稳定基线，不影响连接和通话建立。

## 3. 范围与非目标

### 3.1 本版本范围

- WebRTC APM 硬件/软件 NS 的运行时 A/B 验证。
- 捕获链路原生处理插入点的技术验证。
- RNNoise 原型接入和真实风噪数据验证。
- 风噪场景下的自适应抑制策略评估。
- 运行时诊断、性能采样和失败回退。
- 第一版正式验收只覆盖蓝牙头盔麦克风路线；具体 Bluetooth profile 以真实设备检测结果为准。
- 真机蓝牙头盔路线的音质、延迟、功耗和稳定性验收；手机麦克风、BLE Audio 等路线只做后续探索。
- 运行时必须记录实际 Bluetooth profile；RNNoise 默认启用前必须命中版本内的设备/路线白名单。

### 3.2 非目标

- 用原始 PCM 替换 WebRTC/Opus/RTP 链路。
- 新增第二个录音器或独立音频线程来“旁路”当前 WebRTC。
- 首版提供面向普通用户的降噪等级设置页。
- 处理本地耳机下行播放音频或对远端来音做二次降噪。
- 保证头盔开口、强直吹、麦克风削波或硬件结构性失真可以完全恢复。
- 在未验证 Android 集成成本前直接引入 DeepFilterNet 作为默认算法。
- 云端上传、云端训练或保存用户通话音频。

## 4. 用户与核心场景

### 4.1 主要用户

- 使用 Android 手机和蓝牙头盔的骑行用户。
- 需要在怠速、道路行驶和不同头盔开合状态下进行对讲的用户。
- 不能接受为了降噪而频繁切换设置或手动重连的用户。

### 4.2 场景清单

| 编号 | 场景 | 用户预期 |
| --- | --- | --- |
| S1 | 安静室内通话 | 语音不应比当前基线更差，不能出现明显音色变化 |
| S2 | 发动机怠速 | 发动机低频和持续背景声降低，语音保持自然 |
| S3 | 封闭头盔行驶 | 风噪降低，语音可懂度提升或至少不低于基线 |
| S4 | 头盔开口/强直吹（探索场景） | 允许未通过，不作为首版正式承诺；记录为产品边界 |
| S5 | 蓝牙头盔麦克风（正式路线） | 不因降噪新增卡顿、断续、明显延迟或路由丢失 |
| S6 | 设备不支持或处理过载 | 自动回退到稳定 APM/硬件 NS，不结束通话 |

## 5. 产品决策

### 5.1 默认自动模式

首版不增加用户可见的“低/中/高降噪”设置。降噪模式由经过验证的设备能力和实验配置决定，产品默认只展示“通话降噪已启用”或不展示算法名称。

内部测试可以通过实验开关切换模式，但不能把实验开关暴露给普通用户，也不能让实验配置改变连接、静音或 VOX 业务状态。

### 5.2 保留 WebRTC 主线

WebRTC APM 继续负责 AEC、基础 NS、AGC 和现有音频处理。官方 APM 支持不同噪声抑制等级，并在 WebRTC 音频链路中处理采样率、帧和通道；本产品先围绕现有链路做调优，不迁移到原始 PCM 传输。

### 5.3 一条主降噪路径

硬件 NS、WebRTC 软件 NS 和 RNNoise 不得未经验证地全部叠加。每次 A/B 只改变一个主要降噪变量，保留 AEC，记录实际生效的硬件能力和软件配置。

### 5.4 物理防风是首版边界，不是首版改造要求

风噪进入麦克风膜片后可能产生非线性失真，单麦克风后处理存在上限。首版不要求用户更换麦克风、增加防风罩或改造硬件；验收只针对“头盔闭合 + 普通道路风噪”。头盔开口、强直吹和硬件级风噪问题记录为已知边界，不通过无限提高软件抑制强度解决。

## 6. 功能需求

### FR-01：保持现有实时通话音频链路

1. 继续使用现有 WebRTC PeerConnection、Java Audio Device Module 和 Opus 编码。
2. 不引入原始 PCM TCP/UDP 传输作为降噪实现。
3. 不改变现有 AEC、音频路由、Audio Focus、连接状态和媒体会话所有权。
4. 降噪模块初始化失败时，必须回退到现有稳定音频链路。
5. 降噪模块不得阻塞连接建立、蓝牙切换或通话结束。

### FR-02：运行时实验模式

内部至少支持以下模式，并能在日志中记录实际模式：

| 模式 | 说明 | 发行状态 |
| --- | --- | --- |
| `BASELINE` | 现有 AEC + 硬件/软件 NS 基线 | 默认回退模式 |
| `WEBRTC_SOFTWARE_NS` | 关闭硬件 NS，使用 WebRTC 软件 NS 做 A/B | 内部验证 |
| `WEBRTC_NS_HIGH` | WebRTC APM 高等级 NS，保留 AEC | 内部验证 |
| `RNNOISE_EXPERIMENTAL` | 原生捕获后处理接入 RNNoise | 仅 Debug/内部测试包使用手动开关；正式包无手动开关，仅允许已验证白名单自动启用 |
| `DEEPFILTERNET_OFFLINE` | 仅用于离线或实验设备对比 | 不进入首版默认链路 |

模式切换必须只发生在媒体会话创建或重建边界，不能在音频回调中动态重建 PeerConnection。RNNoise 默认关闭；只有当 APM 未达标且 RNNoise 实验结果有明确收益时，才允许在已验证设备/音频路线启用。正式包不保留手动实验开关；未命中静态白名单时回退到 `BASELINE`。运行时性能判断只用于安全回退，不用于扩大默认启用范围。

### FR-03：风噪抑制策略

1. 风噪检测不能只依赖总音量阈值。
2. 允许综合低频能量、频谱变化、短时平稳度、语音活动和削波情况判断风噪风险。
3. 不能采用固定“低于某个频率全部切除”的单一策略。
4. 风噪抑制应具备自适应强度，语音存在或语音起始瞬态时降低抑制强度。
5. 不能为了降低风噪把远端语音变成明显机器人音、吞字或断续。
6. 发现连续削波时，记录诊断并优先提示进入物理防风/麦克风位置评估，不继续无限增加 DSP 增益或抑制强度。

### FR-04：原生处理插入点

1. 优先验证当前 `stream-webrtc-android:1.3.9` 中的 `ExternalAudioProcessingFactory` 和 `AudioProcessingFactory` 路径。
2. 自定义处理必须位于现有 WebRTC 捕获链路中，并明确其与 AEC、NS、AGC 的相对位置。
3. 如果当前 AAR 的扩展接口不可用，再评估 fork/rebuild WebRTC AAR；不得以第二个 `AudioRecord` 作为默认替代方案。
4. `SamplesReadyCallback` 只允许用于观测、录音测试或统计，不能被当作发送前修改入口。
5. 原生处理失败、帧格式不匹配或回调超时，必须关闭实验模块并回退到 `BASELINE`。

### FR-05：音频帧和采样率

1. 原生处理模块必须明确接收的 PCM 格式、采样率、声道数和每帧样本数。
2. 处理路径应以约 10 ms 音频帧为单位，禁止积累大缓冲造成明显延迟。
3. 必须运行时检测并记录 Bluetooth profile、采样率、声道数和其他实际路线信息；不得假设所有设备都是经典 SCO 或 48 kHz。
4. 如果 RNNoise 或其他算法要求 48 kHz，必须明确重采样位置、质量和 CPU 成本。
5. 不允许在 Java 音频回调中执行可能阻塞的磁盘、网络或大对象分配操作。

### FR-06：性能与实时性保护

1. 每个 10 ms 音频帧的处理时间 P95 不得超过 10 ms；不得持续发生音频回调超时。
2. 音频线程不能因降噪处理触发可听见的爆音、断续、丢帧或路由重建。
3. 需要记录处理耗时、跳帧、回退次数、CPU 和温度变化。
4. 30 分钟通话期间，功耗和温升不得明显劣于当前物理验收基线。
5. 低端设备无法满足实时约束时，自动回退到 `BASELINE`，不弹出算法错误提示，不结束通话。

### FR-07：诊断与可观测性

只记录不包含通话内容的诊断事件：

- `audio_noise_mode_selected`
- `audio_noise_mode_fallback`
- `audio_processing_init_failed`
- `audio_processing_frame_overrun`
- `audio_processing_sample_rate`
- `audio_processing_channel_count`
- `audio_bluetooth_profile`
- `audio_hardware_ns_available`
- `audio_hardware_aec_available`
- `audio_clipping_detected`
- `audio_route_changed`

事件至少包含设备型号、Android API、音频路线、模式、采样率和时间戳。默认不得上传或持久化 PCM、通话文本、联系人信息或远端身份信息。

### FR-08：用户隐私与测试录音

1. 生产版本不保存通话音频。
2. 测试录音必须由测试人员明确授权，并标注设备、头盔、风况和路线。
3. 测试音频只用于本地算法评估，不进入普通日志和崩溃报告。
4. 任何公开样本或训练集必须去除身份信息，并取得相应使用授权。

## 7. 技术方案边界

### 7.1 现有链路中的职责

- `AudioSessionController`：继续负责音频会话生命周期和路由协调。
- `RiderAudioEngine`：继续负责 PeerConnection、媒体轨道、音频设备模块和编码配置。
- 新增的降噪模块：只负责捕获音频处理、指标和回退，不拥有音频路由，不改变连接状态。
- `SamplesReadyCallback`：继续作为观测入口，不承担发送音频修改。

### 7.2 推荐处理拓扑

```text
麦克风 / Bluetooth SCO
        |
        v
WebRTC Audio Device Module
        |
现有 AEC / APM 基础处理
        |
可选的自定义捕获后处理（RNNoise / 风噪检测）
        |
Opus 编码 + FEC/DTX
        |
WebRTC 传输
```

上图是产品目标拓扑，具体处理顺序必须以实际 WebRTC APM 和 AAR 验证结果为准。AEC 不得因接入 RNNoise 或其他算法而被绕过。

### 7.3 兼容与回退

- 硬件 NS 可用且经过验证时，允许作为 `BASELINE` 的一部分。
- 硬件 NS 不可用时，使用 WebRTC 软件 NS 或稳定默认路径。
- 自定义模块不可用时，不影响 AEC、Opus、路由和通话。
- 不新增独立的 `AudioRecord`、`AudioTrack` 或第二套回声消除链路。

## 8. 开源方案决策

| 方案 | 适用定位 | 主要收益 | 主要风险 | 处理结论 |
| --- | --- | --- | --- | --- |
| WebRTC APM | 默认基础能力 | 已在工程链路中，低延迟，包含 AEC/NS/AGC | 设备硬件 NS 行为不一致，极端风噪有限 | P0 首选 |
| RNNoise | 条件性原生增强 | BSD-3-Clause，48 kHz/10 ms 实时模型，适合非平稳噪声 | 非风噪专用，需要 JNI、重采样和真实数据调参 | 仅在 APM 未达标时 P1 Spike |
| DeepFilterNet | 质量上限评估 | 全频带 48 kHz，有实时实现，MIT/Apache-2.0 | Android 封装、CPU、内存和延迟成本高 | P2 评估 |
| SpeexDSP | 轻量基线 | 有 NS、AGC、VAD，部署简单 | 算法较老，不针对摩托车风噪 | 仅作对照 |
| 双麦/接触式麦克风 | 硬件路线 | 可利用空间/接触信号区分风噪和语音 | 需要产品硬件变化 | 极端风况备选 |

## 9. 测试与验收方案

### 9.1 测试条件

必须在安全、可重复的条件下采集，不要求测试人员在开放道路上为了达到某个速度冒险。测试条件至少覆盖：

| 类别 | 条件 |
| --- | --- |
| 环境基线 | 安静室内、普通室内背景声 |
| 机械噪声 | 发动机怠速、道路背景声 |
| 风噪 | 正式门槛为头盔闭合 + 普通道路风噪；头盔开口、强直吹、极端风强只作探索记录 |
| 语音 | 男声、女声、短句、连续通话、数字和地名 |
| 音频路线 | 正式门槛为蓝牙头盔麦克风；手机麦克风、BLE Audio 只作探索，不作为首版通过依据 |
| 设备 | 发布前至少需要一台真实 Android 手机和一套蓝牙头盔；第二 OEM 设备为推荐增强项 |
| 样本 | 阶段一可用公开风噪语音样本做算法预验证；阶段二必须使用真实蓝牙头盔，公开样本不能替代正式听音证据 |
| 时长 | 单次短句 A/B，至少一次 30 分钟稳定性测试 |

测试分两阶段：阶段一使用公开样本、合成音频和室内设备验证帧处理、趋势和失真；阶段二使用真实蓝牙头盔，在安全、可重复的条件下验证头盔闭合 + 普通道路风噪。每个样本必须记录设备、Android API、头盔/麦克风型号、麦克风位置、防风材料、风向、风况、路线、Bluetooth profile、降噪模式和版本号。当前真实设备和具体风噪测试方法尚未确定；在方法和设备确定前，物理项目保持 `Not Run`。

### 9.2 质量指标

- 语音可懂度：STOI 或等价指标，加人工盲听。
- 噪声效果：分段 SNR、低频噪声能量、风噪主观评分。
- 失真：语音失真、吞字、机器人音、削波率。
- 实时性：每帧处理耗时、P95 延迟、音频回调超时、丢帧和回退次数。
- 系统性：CPU、内存、温度、电量、蓝牙路由稳定性和 30 分钟通话状态。

Phase 0 先建立当前 `BASELINE` 的实测值，再锁定最终数值门槛。当前产品验收不设死的 dB 或百分比目标，必须满足“安静场景不变差、目标风噪场景人工听感改善、语音不吞字”。未完成基线或没有真实蓝牙头盔设备前，可以继续软件开发，但相关物理验收必须标记为 `Not Run`，不得宣称降噪发布通过。

### 9.3 必须满足的验收条件

- [ ] 安静和普通道路场景下，语音可懂度不低于 `BASELINE`。
- [ ] 头盔闭合 + 普通道路风噪场景下，人工盲听确认清晰度改善，且没有吞字。
- [ ] 人工听音以远端听音者比较同一句话的 A/B 输出为准；本地回放不能替代远端听感。
- [ ] 不新增持续爆音、卡顿、断续、明显机器人音或远端听不到语音。
- [ ] 音频处理 P95 不超过 10 ms/10 ms 帧，且无持续回调超时。
- [ ] 30 分钟通话的 CPU、温度、电量和路由稳定性不劣于当前物理基线。
- [ ] AEC、Opus、FEC/DTX、静音、VOX 和通话状态不发生语义回归。
- [ ] 处理初始化失败或过载时回退到 `BASELINE`，通话不被结束。
- [ ] 正式测试覆盖蓝牙头盔麦克风路线；手机麦克风、BLE Audio 和第二 OEM 属于后续扩展项。
- [ ] 所有实验模式、回退和实际采样率均可从诊断日志确认。
- [ ] 运行时 Bluetooth profile 与静态设备/路线白名单匹配结果可从诊断日志确认。
- [ ] 人工听音证据与自动化指标分开记录，不能用模拟器或 JVM 测试代替物理听音。
- [ ] 没有真实蓝牙头盔和手机时，物理风噪验收标记为 `Not Run`，不能作为发布通过证据。

### 9.4 现有验收文档补充

当前 [release-candidate-physical-plan.md](../verification/release-candidate-physical-plan.md) 已覆盖蓝牙、麦克风、AEC、人耳听音和 30 分钟稳定性，但缺少专门的风噪条件和风噪质量指标。本需求实现时必须新增风噪测试矩阵，不得只复用短语通话通过结果。

## 10. 实施阶段

### P0：基线与 APM 验证

- 增加内部实验开关和诊断字段。
- 固定当前代码原样为 `BASELINE`，先完成不改音频行为的诊断和 APM A/B。
- 核实硬件 AEC/NS 的可用性和真实生效状态。
- 对比硬件 NS、WebRTC 软件 NS 和不同 APM 等级。
- 建立风噪录音集、人工盲听表和基础指标。
- 不改变默认发布行为，确保现有通话链路可回退。

### P1：原生处理 Spike 与条件性 RNNoise

- 验证当前 1.3.9 AAR 的 `ExternalAudioProcessingFactory`/`AudioProcessingFactory` 是否可在 Android 真机稳定调用。
- 确认处理顺序、采样率、帧大小、JNI 边界和线程实时性。
- 只有 P0 证明 WebRTC APM 未达到目标时，才接入 RNNoise 实验模式。
- RNNoise 只在 Debug/内部测试包使用隐藏开关和静态设备/路线白名单；单台真实设备通过即可仅对该设备/路线启用，其他设备回退到 `BASELINE`，正式包移除实验开关。
- 如果 WebRTC APM 已满足“安静场景不变差、目标风噪场景人工听感改善、语音不吞字”，直接结束 RNNoise 产品化，不继续增加算法复杂度。

### P2：高质量方案与硬件评估

- 对 DeepFilterNet 做离线质量和 Android 性能评估。
- 评估自适应风噪检测、低频保护和削波风险处理。
- 如果软件方案在目标风况下仍不达标，记录为首版产品边界；双麦克风、接触式或骨传导硬件不在本 PRD 实施范围。

### P3：发布与灰度

- 默认模式只使用通过验收的路径。
- 低端或不兼容设备自动使用 `BASELINE`。
- 实验开关和音频样本采集不得进入普通用户版本。
- 没有真实设备听音证据时，发布记录必须保留 `Not Run`，不得写成“风噪降噪已验收”。
- 没有真实设备听音证据时，正式包只启用 `BASELINE`；降噪增强功能不得默认打开。
- 发布前完成许可证、NOTICE、性能、隐私和真机证据审查。

## 11. 风险与防护

| 风险 | 影响 | 防护 |
| --- | --- | --- |
| 1.3.9 AAR 的预处理回调未接通 | 接入后实际不处理发送音频 | 先做运行时 Spike；失败则使用正式原生工厂或重编 AAR |
| 硬件 NS 在 OEM 间差异大 | 同一配置音质不一致 | 记录可用性和实测效果；硬件/软件 NS 做 A/B |
| 降噪叠加过度 | 机器人音、吞字、语音变薄 | 一次只启用一个主要 NS；保留人工盲听 |
| 蓝牙采样率变化 | RNNoise 重采样、延迟或音质问题 | 运行时记录采样率；把重采样纳入性能测试 |
| 设备/路线白名单过窄或过宽 | 兼容设备未启用或不兼容设备音质回归 | 以真实 A/B 结果维护静态白名单，运行时只允许回退，不自动扩容 |
| DSP 过载 | 爆音、卡顿、通话中断 | 每帧计时、超时回退、30 分钟热稳定性测试 |
| 麦克风直接受风或已削波 | 软件无法恢复语音 | 防风罩、位置和硬件路线纳入验收 |
| 第三方许可证/专利 | 发布合规风险 | 固定版本、审查 LICENSE/NOTICE/PATENTS，禁止复制 AGPL 代码 |
| 测试录音含个人信息 | 隐私泄露 | 明确授权、仅本地使用、脱敏和生命周期清理 |

## 12. Definition of Done

- [ ] PRD 中的 P0 基线和风噪测试集已建立。
- [ ] WebRTC APM 硬件/软件路径的实际生效状态已验证。
- [ ] 原生处理插入点已通过 Android 真机 Spike。
- [ ] RNNoise 是否进入下一阶段有数据依据，而不是只凭主观感觉。
- [ ] 已明确 APM 达标时无需继续 RNNoise 产品化。
- [ ] 处理延迟、CPU、内存、温度和电量通过门禁。
- [ ] 安静、道路、怠速、头盔开口/闭合和侧风场景完成 A/B。
- [ ] 自动化音频状态测试和人工听音证据均已归档。
- [ ] 失败回退不会结束通话或破坏路由。
- [ ] 许可证、隐私和测试样本处理完成审查。
- [ ] 只有通过全部门禁的模式才能成为默认发布模式。

## 13. 最终产品原则

1. 保留 WebRTC 主线，不用原始 PCM 项目替换实时通话架构。
2. 先证明音频样本确实经过自定义处理，再讨论算法效果。
3. 风噪不是单纯的低频噪声，固定低切不能作为完整方案。
4. 语音可懂度优先于“噪声数值看起来更低”。
5. 硬件防风和麦克风位置与 DSP 同等重要。
6. 算法失败时回退到稳定通话，不让降噪功能破坏连接、路由和 AEC。
7. 所有“降噪有效”的结论必须同时有客观指标和人工听音证据。
