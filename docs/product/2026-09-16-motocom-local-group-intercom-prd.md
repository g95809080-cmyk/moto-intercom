## 1. 产品目标与非目标

### 1.1 目标

- 没有蜂窝信号、没有互联网、没有现场路由器时，附近 Android 手机仍可建立最多四人的实时对讲。
- 组队前允许必要的系统授权或 Wi-Fi 加入操作；应用内的普通入队使用六位码，不逐个请求房主批准。
- 默认全双工，所有成员都可以同时讲话；各自控制本机收听与麦克风。
- 普通成员进退、短暂掉线、来电不应停止其他健康链路的通话。
- 保留现有双人模式，继续兼容旧版双人客户端。
- 状态反映真实连接与音频情况，不能把“已加入”当作“全队都能听说”。

优先级：稳定和语音可懂度 > 低延迟 > 续航与距离 > 扩人数和高保真音质。不得用降低首版人数或取消已确认功能的方式静默绕过验收问题。

### 1.2 非目标

- 蜂窝网络通话、云端房间、互联网 STUN/TURN/SFU 作为必需依赖。
- iOS、多平台混合首发、大型车队、长距离覆盖或无线多跳中继。
- 首版超过四人、无限人数、房主/网络主机无缝迁移。
- 长期车队、账号、社交、定位分享、录音、广播巡游、抢麦和领队语音优先。
- 正在进行的双人通话无缝升级为多人，或同时参加双人和多人通话。
- 替其他成员强制开麦、全队禁言。
- 提前实现更大规模媒体服务器或更换音频引擎。

“未来扩人数”要求容量规则集中管理、成员按集合建模，不把四个固定席位散落在 UI、协议和媒体代码中；不要求现在实现六人或八人。

## 2. 术语与身份

| 术语 | 定义 |
| --- | --- |
| 房主 | 创建本次临时队伍的成员，负责结束队伍、移除成员和解除入队限制 |
| 网络主机 | 提供本地网络的设备，例如 Wi-Fi Direct Group Owner；不与产品房主概念混用 |
| 队伍实例 | 一次创建到结束的运行时队伍，拥有独立内部身份和生命周期 |
| 六位入队码 | 本次队伍的入队凭据；不是 Wi-Fi 密码、稳定设备 ID 或全局唯一队伍 ID |
| 已加入 | 入队凭据、身份、容量及移除限制等校验通过，进入本次成员名单 |
| 语音链路就绪 | 某一对成员的双向媒体路径、音频 I/O 和路由已得到有效确认 |
| 全队语音就绪 | 当前参与通话的每对成员均具备双向音频链路；不是都连上房主就算就绪 |

内部队伍身份必须独立于六位码，防止随机码重复、结束后重建和迟到回调造成串队。进程重建不得仅凭同一个码恢复旧队伍授权。具体标识和协议布局在技术设计中确定。

## 3. 用户流程

### 3.1 创建队伍

选择多人模式 → 创建临时队伍 → 准备本地网络 → 显示随机六位码与等待状态 → 队友加入 → 逐条建立语音链路。

网络准备失败时明确展示失败阶段或必要的系统操作，不显示“队伍可加入”或“语音就绪”的假成功。码可在准备期间生成，但其展示必须与当前准备状态一起呈现。

### 3.2 加入队伍

输入六位码 → 查找附近匹配队伍 → 必要时完成系统网络准备 → 校验入队资格与容量 → 自动加入 → 与现有成员建立语音链路。

- 正常情况不需要从设备列表选择房主，不需要房主逐个接受。
- 附近多个同码队伍同时被发现时，显示房主昵称等识别信息，额外选择一次。
- 不自动合并同码队伍，不因某个队伍先响应就误加入。
- 找不到队伍、网络未准备好、入队验证失败、版本不兼容、已满员、被移除限制、语音未就绪应有可区分的状态；未发现目标不能直接报告为口令错误。
- 系统授权和 Wi-Fi 操作不属于房主审批，不承诺六位码能绕过系统要求。

### 3.3 运行中

已就绪的成员链路先听说；新成员的慢链路不拖停现有成员。成员列表展示个人状态，本机可静音自己或屏蔽特定成员。途中仍允许凭码加入，不打断正在进行的语音。

## 4. 功能需求

### FR-01 模式与兼容性

- 双人和多人提供独立创建/加入路径，同一时刻只参加其中一个通话。
- 多人成员必须使用支持本次群组协议的版本；旧版客户端继续使用原有双人协议。
- 多人期间收到双人请求返回忙碌，不中断队伍、不抢占媒体资源。
- 用户主动切换模式时，先明确退出当前通话。房主切换模式也必须遵守结束全队的确认规则。
- 群组发现和消息不能被旧版误解释为普通双人自动连接。

### FR-02 入队码

- 每次新建队伍随机生成一个固定长度六位数字字符串，整场队伍保持不变。
- 成员加入、退出、短暂掉线或恢复，不触发换码。
- 所有已加入成员都能查看并口头分享；知道码的附近成员在满足容量和限制条件后自动加入。
- 不新增第二套普通入队审批。房主解除被移除成员限制不属于普通入队审批。
- 队伍结束时本次码失效；以后即使偶然生成同码，也属于新的队伍实例，不能复活旧连接。
- 自动重连运行中的原队伍不需要重复输入；进程重启后的规则见 FR-08。

### FR-03 容量与并发入队

- 四人上限包含房主、当前已加入成员和仍被保留的掉线成员名额。
- 多个同时入队请求的最终准入必须串行或原子处理，不能瞬间超员。
- 已满员时明确告知，不挤走现有成员。
- 未完成入队的临时握手资源不得永久占位；取消、失败或过期需要回收。
- 入队容量的唯一裁决者、预留事务及超时参数在设计中明确，不在各手机各算一份后假定一致。

### FR-04 全双工与本机静音

- 所有人可同时讲话，无抢麦或领队强制优先。
- 自静音停止向所有队友发送自己的语音；VOX 与既有个人音频控制继续协调。
- 屏蔽特定成员仅影响本机播放，不阻止该成员向其他人发送，不改变其他人的收听。
- 本机成员静音在本次队伍内跨掉线重连保留；主动离队或队伍结束后清除，不通知被屏蔽者。
- 来电暂停与恢复不能重置用户原有自静音及本机成员静音设置。
- 主动静音、VOX 静默等正常行为不能被当成链路掉线；验收需在解除静音、实际讲话条件下确认每对成员互听。

### FR-05 成员管理

- 房主可以移除成员，被移除者停止参与媒体及自动重连，并获知被移除的结果。
- 被移除者在本次队伍内再次输入正确码也不能直接回来。
- 房主主动解除该成员的限制后，成员可以重新凭码加入；不需要另加审批。
- 限制属于本次队伍，不扩展为长期账号或跨队伍封禁。身份识别需复用并核实项目既有稳定设备身份，不能只以昵称或 IP 区分。
- 同队不自动保存双人配对，不破坏既有双人配对记录。

### FR-06 普通成员掉线

- 意外掉线时仅恢复该成员相关链路，正常成员继续通话。
- 自检测到掉线起保留名额 60 秒，显示“重连中”；超时释放名额并继续低频寻找原队伍。
- 释放名额后，原成员恢复且队伍有空位时自动重新准入；已满员则等待，不挤走新成员。
- 不得因同码、同昵称或先响应而连接到其他队伍。
- 重试只在用户仍有参与原队伍意图、原队伍未确认结束、未被移除且当前运行时有效时继续。
- 主动离队立即撤销恢复意图；迟到回调不能重新入队或开麦。
- 低频重试间隔、抖动抑制与部分媒体失败的判定参数由设计和实测确定，不改变上述产品语义。

### FR-07 房主退出与网络主机失联

- 房主主动退出前确认“将结束所有成员的对讲”，确认后结束全队，撤销本次入队和重连资格。
- 收到有效队伍结束消息的成员显示原因并停止重连。
- 失联不等于收到结束通知；暂时联系不上房主时不得伪造“房主已结束队伍”。
- 网络主机失联允许全队短暂中断，尝试恢复原网络/队伍；首版不承诺无缝换主。
- 恢复失败时显示可执行提示，允许停车后重新建队，不静默迁入其他队伍。
- 房主与网络主机是否由同一设备承担、如何维持成员一致性及判断恢复失败，需在技术设计中明确。

### FR-08 进程与后台生命周期

| 情况 | 产品行为 |
| --- | --- |
| 正常切后台或锁屏，进程仍运行 | 保持对讲与必要的运行时资源，不视为离队，不要求重输码 |
| 普通成员短暂断网，进程仍运行 | 按 FR-06 自动找回原队伍 |
| 普通成员进程终止/重启 | 不自动入队、不自动开麦；再次打开后重新输入口令，仍受本次被移除限制约束 |
| 房主短暂断网，进程仍运行 | 尝试恢复原队伍，码不因断网而变化 |
| 房主进程终止、崩溃或手机重启 | 不恢复跨进程旧队伍；需要重新创建并生成新码，其他成员通过失联流程处理 |
| 房主主动结束 | 按 FR-07 通知结束并撤销运行时资源 |

不能把页面重建、Activity 重建或普通后台切换误当成进程终止。用户停止后，旧 generation、socket、网络、音频和焦点回调不能恢复通话。

### FR-09 空队伍

- 只剩房主时保留队伍和原码，显示“等待成员加入”，不因暂时无人自动解散。
- 没有远端成员时不持续采集麦克风；保留必要的发现、入队和网络能力。
- 有远端成员再次进入后，按有效媒体需求恢复采集和播放，不残留上一次已释放的媒体上下文。

### FR-10 来电与音频中断

- 某位成员来电时，仅暂停该成员的对讲录音和播放，其他成员继续交流。
- 如果该成员承担网络或房间协调职责，暂停音频不能顺带释放这些仍需存活的资源。
- 其他成员显示“音频暂不可用”，不展示电话原因。
- 电话结束后，在系统焦点、路由和用户参与意图允许时恢复，保留静音设置。
- 继续遵守既有电话隔离、蓝牙路由和音乐/导航共存规则，不控制第三方 App 全局音量。
- 本条仅在多人模式中替代旧多音频 PRD 的“远端完全无感知”要求；不擅自改变旧版双人协议。

### FR-11 就绪与反馈

- 将“网络准备”“已加入队伍”“个人音频暂不可用”“部分成员互通”“全队语音就绪”区分开。
- 已就绪链路允许先听说，不因慢成员而暂停正常语音。
- 四人全互通涉及六对成员链路，不能仅检查三条房主连接。
- 全队就绪需来自各链路的真实确认；最终验收包含每对双向听音，不能仅用 TCP、SDP、ICE 或名单更新证明声音可用。
- 成员卡片明确反映异常及尚未互通关系；UI 表达形式由设计确定，但用户必须能理解谁暂时听不到谁。
- 异常和恢复各给一次简短提示音；合并网络抖动事件，不连续播报、不盖过语音。
- 本机主动屏蔽、用户自静音与链路故障是不同状态，不混为“对方已掉线”。

## 5. 规则替代关系

- 六位码自动入队替代访谈早期“每个新人由房主批准”的方案。
- 房主解除限制后可凭码重入，替代早期“被踢后重新申请审批”。
- 多人模式是新增产品范围，不将历史 PRD 的“一对一非目标”理解为本次禁止实现；双人模式原有契约继续保留。
- 多人媒体将涉及对单活跃媒体会话假设的改变。既有 KUM-37 的音频平台共享、资源所有权和串行状态原则应复用，单会话上限的调整须通过新架构审查，不能声称旧审批自动覆盖。

## 6. 技术方向与必须先核实的事实

以下是研究建议和设计约束，不把未验证实现细节伪装成用户确认的产品能力。

1. 保留 WebRTC / Opus 与现有音频路由、电话协调、前台服务和身份机制。
2. 首选验证四人 full mesh：每台一次麦克风采集，共享本地音轨，面向另外三人分别建立 PeerConnection，接收端混合播放。共享采集不等于只编码一次。
3. 每个成员拥有独立连接/恢复上下文，公共采集、音频设备、factory 和房间网络资源拥有独立生命周期；单人离开不能释放其他成员依赖的公共资源。
4. 房间信令协调与媒体转发分开。所有人各连一个普通房主 PeerConnection，不会自动让队员互相听见；如要改为 SFU/MCU，必须另做技术论证，不默认更换路线。
5. 先在共同 LAN 验证媒体，再完成无路由器的 Wi-Fi Direct 群组或本地热点方案。共同 LAN 只是阶段验证，不是最终产品前提。
6. 输入六位码后、尚未处于共同 IP 网络时，如何发现候选队伍并准备网络，必须做明确设计/验证；不能以“先手动加入同一 Wi-Fi”冒充完整的无路由器闭环。
7. 实测多个 Wi-Fi Direct/热点客户端间的可达性、设备人数限制、原生 WebRTC 多轨混音、旧机 CPU/功耗、蓝牙与后台行为。四人容量尚未被真机证明。
8. 新群组信令要有显式版本/能力边界；现有 V2 严格拒绝未知字段，不能不做兼容设计就直接追加群组字段。
9. 入队凭据有效性、成员资格、房主权限、已移除限制和容量必须在媒体开放前校验；发现信息不能把入队码作为人人可读的公开字段。具体方案写入技术设计。
10. 本次不得因未来扩容而加入未需要的通用会议框架、多音频引擎或云服务。

## 7. 体验与性能目标

- 首次建联一分钟、再次建联三十秒是待验证的体验目标，不是已达到的保证。分别记录网络准备、入队验证、首次可听和全队就绪耗时；标记等待系统授权/用户操作的时间，避免口径混淆。
- 先通过连续两小时四人稳定性测试，随后执行四小时观察；保留温度、CPU、耗电、丢包、延迟、断线和恢复记录。
- 功耗比较使用相同导航、耳机、亮度和网络条件下的对照，不先写固定耗电百分比。
- 不承诺尚未实测的距离、延迟阈值、更高人数或所有 OEM 行为。
- 实测达不到目标时报告具体瓶颈和证据；不得静默把“最多四人”改成“只验证双人”。

## 8. 验收矩阵

### 8.1 自动化与兼容性

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| A01 | 创建、结束、重建 | 六位码在同次队伍中稳定；结束后旧实例无效；同码不复活旧实例 |
| A02 | 自动入队 | 正确凭据且有容量自动加入，无普通房主审批；错误/不支持版本不开放媒体 |
| A03 | 同码多队 | 展示候选并按所选真实队伍身份加入，不合并、不误连 |
| A04 | 并发与满员 | 含房主最多四人；并发准入不超员；取消/失败握手不永久占位 |
| A05 | 掉线占位 | 60 秒内保留；到期释放；有空位恢复、满员等待，不驱逐当前成员 |
| A06 | 取消与迟到事件 | 主动退出/结束/旧 generation 后，无自动开麦、重连或状态污染 |
| A07 | 移除与解除 | 正确码不能绕过移除限制；房主解除后才允许重入 |
| A08 | 静音 | 自静音影响自己的发送；成员静音只影响本机；重连保留、离队清除，不影响其他成员 |
| A09 | 来电 | 仅本机音频暂停/恢复，状态不透露电话原因，网络和其他成员媒体不随之释放 |
| A10 | 空队伍 | 只剩房主仍可发现/加入，不持续采集麦克风，再加入时可恢复音频 |
| A11 | 进程和后台 | 后台/页面重建不离队；进程重启不自动复活队伍、入队或开麦 |
| A12 | 部分就绪 | 可用链路先通话；状态按成员关系汇总，不将部分互通显示为全队就绪 |
| A13 | 双人兼容 | 旧版双人连接不回归；多人时双人请求忙碌；模式切换无资源交叉污染 |
| A14 | 配对与权限 | 群组不自动写双人配对；非房主不能执行结束全队、移除/解除限制 |
| A15 | 资源清理 | 单连接释放不关闭其他人；全队结束后资源释放，不残留采集、socket 或恢复任务 |

### 8.2 真实设备

| 编号 | 场景 | 通过条件 / 证据 |
| --- | --- | --- |
| D01 | 三人共同 LAN | 三对成员逐一双向听音成功，验证多人媒体基础 |
| D02 | 四人共同 LAN | 六对成员逐一双向听音；多人同时讲话可用，无自声回传或明显啸叫 |

| D04 | 中途加入、退出、重新加入 | 已有健康链路不中断；旧回调、旧名单不污染当前队伍 |
| D05 | 掉线 60 秒边界与满员恢复 | 名额保留/释放符合 A05；返回成员不挤走新人 |
| D06 | 房主主动结束及主机失联 | 主动结束停止重连；失联显示恢复而非假结束；失败有重建路径 |
| D07 | 房主及普通成员进程终止/重启 | 分别符合 FR-08；不伪装旧队伍仍有效，不自动开麦 |

| D09 | 蓝牙、手机路由、后台和来电 | 路由切换和来电隔离正确，其他成员继续交流；电话后保留静音设置 |
| D10 | 两小时稳定性及四小时观察 | 记录四机型号/系统/构建 SHA、耗电温度、延迟丢包、断线恢复与主观听音 |

## 9. 实施顺序与 Git 管理

### 9.1 阶段

1. 读取 `AGENTS.md`、本 PRD、既有架构和验证记录，记录干净基线及工作区边界。
2. 在 Linear 查找/绑定本需求的 issue，按项目约定建立 Rasen proposal/design/tasks；不虚构 issue 编号、不重排无关路线。
3. 完成协议兼容、队伍身份/准入、资源所有权、六位码发现建网和恢复状态设计；依项目约定完成架构审查，再进入相应源码行为变更。
4. 先实现可验证的队伍域模型、协议及自动化，再完成三人/四人媒体与 UI；具体 issue 拆分以 Linear 为准。
5. 完成无路由器凭码闭环、音频控制、成员进退和恢复，不停留在 LAN 演示版。
6. 做与改动相称的回归、构建和真实设备验收，提交清晰证据，区分实现完成与硬件验收未完成。

上述为依赖顺序建议，不代替 Linear 路线，也不把每个阶段自动等同于一个已创建 issue。

### 9.2 Git 与工作区边界

- 本 PRD 在 `docs/local-group-intercom-prd` 上单独提交，方便追溯需求基线。
- 新执行任务只在 `MotoIntercomApp-local-group` 工作。不要直接编辑其他 worktree，更不要使用项目容器根目录中的散落旧源码。
- 在 PRD 提交基础上建立与真实活动 issue 对应的实现分支；每个活动 issue 对应一个 Rasen change、一条实现分支和一个独立可审查 PR，遵守 `AGENTS.md`。
- 最大并发写入者为一个；审查可以只读进行。提交采用小而完整的逻辑单元，包含相关实现、适量测试及必要说明，不混入其他工作区内容。
- 每次提交前检查 `git diff --check`、差异范围和相称测试；使用明确路径暂存，不使用无差别 `git add -A` 收进用户工作。
- 不强推、不重写已有公共历史、不自动合并 main、不签名发布或部署。阶段结果保留提交 SHA、测试结果及未解决项。
- Rasen 命令遵守 `DO_NOT_TRACK=1`、`RASEN_TELEMETRY=0`。架构审查报告遵守项目规定的状态、P0/P1、Base/Head SHA 和下一门禁格式。
